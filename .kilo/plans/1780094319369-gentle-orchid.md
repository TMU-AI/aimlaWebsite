# AI-Native Architecture Document Plan

## Goal
Produce one primary architecture document for the club's summer project that is detailed enough to let multiple junior developers work in parallel without drifting on system shape, interfaces, or invariants.

## Document Intent
- Clarify the system as an AI-mediated information interface, not a general chatbot.
- Freeze the core contracts that affect cross-team integration.
- Leave room for local implementation flexibility inside each subsystem.
- Include concrete example inputs, outputs, and test cases so contributors can build against shared expectations.

## Recommended Deliverable Shape
Create a single main document in `docs/architecture/` focused on the target system, with appendices inside the same document rather than splitting the first draft across many files.

Recommended title:
- `AI-Native Website Architecture`

Recommended audience:
- Project leads and subsystem owners first.
- Junior contributors second.
- Future handoff maintainers third.

## Confirmed Architectural Position
The document should explicitly commit to these points near the top:
- Canonical information is deterministic and structured.
- The LLM is non-authoritative and optional.
- The system is a constrained guided interface, not an open-ended chatbot.
- Session state is reconstructed from compact event/state metadata, not raw HTML dumps.
- The frontend experience should feel dynamic and conversational while remaining largely cacheable and operationally simple.
- The project should optimize for an architecturally disciplined core with an experimentally flexible surface.

## Core Decisions To Freeze Early
These are the parts that should be treated as stable contracts in the document:
- Session state model.
- Event log shape and reconstruction rules.
- Frontend/backend boundary.
- Intent router contract.
- Structured content schema ownership.
- Persistence format for shareable sessions.
- LLM transformation boundary and allowed behaviors.
- Caching tiers and cache key strategy.

## Recommended Document Outline

### 1. Purpose And Product Framing
Define:
- What the system is.
- What the system is not.
- Why the architecture is constrained this way.

Include explicit non-goals:
- No general-purpose chatbot behavior.
- No LLM-generated canonical facts.
- No opaque UI state that cannot be reconstructed deterministically.
- No raw HTML persistence.

### 2. Architectural Invariants
List the rules every subsystem must preserve.

Recommended invariants:
- Structured content is the source of truth.
- Retrieval happens before any LLM transformation.
- LLM output cannot change identifiers, links, dates, or canonical facts.
- Every rendered panel must be reproducible from serialized state plus canonical content.
- Session URLs must encode or reference compact state, not full markup.
- The system must degrade gracefully when the LLM is disabled or unavailable.

### 3. System Context
Describe major subsystems and data flow at a high level:
- Structured content layer.
- Intent router.
- Content retrieval layer.
- Optional LLM transformation layer.
- Streaming renderer.
- Session persistence layer.
- Caching layer.

Include one simple request lifecycle example:
- User selects prompt.
- Intent is resolved.
- Structured content is fetched.
- Optional transformation is applied.
- Renderer emits event stream.
- Session state is updated and persisted.

### 4. Canonical Data Model
Define the content layer first because every other subsystem depends on it.

Document should include:
- Main content entity types such as `page`, `section`, `event`, `team_member`, `faq`, `cta`, `link`.
- Stable IDs for all entities.
- Required versus optional fields.
- Rules for references between entities.
- Validation rules.

The document should include at least one concrete JSON example for:
- An event record.
- A team record.
- A guided prompt definition.
- A retrieved content bundle returned to the renderer pipeline.

### 5. Intent Router Contract
Define the input/output boundary clearly enough that frontend and backend contributors can work independently.

Document should specify:
- Accepted intent types such as `open_section`, `compare_events`, `show_team`, `suggest_next`, `summarize_content`.
- Allowed inputs from UI.
- Router output shape.
- Confidence or fallback behavior.
- Rejection behavior for unsupported or out-of-scope queries.

Include example router payloads:
- Input UI action.
- Routed intent.
- Retrieval query derived from that intent.

### 6. Retrieval Layer Contract
Define how deterministic content is fetched.

Document should specify:
- Retrieval inputs.
- Filters and sort behavior.
- Output schema.
- Empty-state behavior.
- How retrieval metadata is attached for later rendering and analytics.

Include example outputs:
- Event list retrieval.
- Single club initiative retrieval.
- Suggested next prompts based on current context.

### 7. Optional LLM Transformation Boundary
This section is critical because it prevents chatbot scope creep.

Document should specify:
- When the LLM may be invoked.
- What fields it receives.
- What it may return.
- What it must never alter.
- Fallback behavior when disabled, rate-limited, or low-confidence.

Recommended allowed functions:
- Paraphrase.
- Tone styling.
- Summarization.
- Lightweight personalization.

Recommended forbidden functions:
- Inventing unavailable facts.
- Changing canonical metadata.
- Performing tool orchestration beyond allowed contracts.
- Answering unsupported freeform queries as if authoritative.

Include one example transformation pair:
- Deterministic input bundle.
- Safe transformed output bundle.

### 8. Streaming Renderer And UI Reconstruction
This should be one of the most detailed sections because it coordinates frontend contributors.

Document should specify:
- Renderer input contract.
- Event types emitted to the UI.
- Panel or block model.
- Progressive assembly behavior.
- Rules for expand/collapse state.
- Rules for replaying from persisted session state.

Recommended event examples:
- `session_started`
- `intent_resolved`
- `panel_added`
- `text_stream_started`
- `text_stream_delta`
- `text_stream_completed`
- `panel_expanded`
- `panel_collapsed`
- `suggestions_updated`

Include a serialized session example showing how a session can be replayed without storing markup.

### 9. Session Persistence And Shareable URLs
Define exactly what is saved and what is regenerated.

Document should specify:
- Session identifier model.
- Stored metadata versus derived UI.
- Revision/version field for forward compatibility.
- URL/share behavior.
- Session hydration flow.
- Expiry and cleanup assumptions if applicable.

Include one example persisted state payload with:
- Session ID.
- Ordered event list.
- Active panel states.
- Current suggestion context.
- Retrieval references.
- Optional LLM variant references or cache keys.

### 10. Caching And Delivery Strategy
Document the "static generation disguised as dynamic intelligence" idea in explicit layers.

Recommended layers:
- Static assets and base shell.
- Cached canonical retrieval responses.
- Cached transformed variants.
- Live generation fallback.

Document should define:
- What cache keys are based on.
- What invalidates each tier.
- Which layers are safe to serve stale.
- How the system behaves when only deterministic content is available.

### 11. Frontend/Backend Boundary
This section should be written as hard interface contracts rather than implementation preferences.

Freeze:
- API endpoints or local adapter boundaries.
- Request and response schemas.
- Streaming protocol choice.
- Error envelope shape.
- Versioning expectations.

Even if the first slice is static-first, define the future service boundary now so frontend and backend teams can work concurrently against mocks.

### 12. Testing Strategy And Contract Examples
The architecture document should include tests as executable design guidance, not only prose.

Recommended test categories:
- Schema validation tests for canonical content.
- Intent routing tests.
- Retrieval determinism tests.
- LLM guardrail tests.
- Renderer replay/reconstruction tests.
- Session serialization/deserialization tests.
- Cache key consistency tests.
- Unsupported-query behavior tests.

Recommended concrete example tests to include in the document:
- Given a valid `show_team` intent, the router returns the correct retrieval query.
- Given a structured event record, the retrieval layer returns stable sorted output.
- Given LLM augmentation is disabled, the renderer still produces a complete deterministic experience.
- Given a saved session, replay reconstructs the same panel order and visible content.
- Given an unsupported freeform prompt, the system responds with constrained suggestions instead of chatbot improvisation.

### 13. Team Ownership And Parallel Work Model
Document ownership boundaries so juniors know where they can move fast safely.

Recommended ownership split:
- Frontend/rendering: panel model, animation, stream presentation, replay behavior.
- Backend/APIs: session persistence, retrieval services, cache orchestration, content APIs.
- AI/routing: intent classification, safe transformation contracts, fallback behavior.
- Infrastructure/CI-CD: deployment, preview environments, schema validation in CI, observability.

Document should also define integration surfaces owned jointly:
- Shared schemas.
- Mock payloads.
- Event contracts.
- Versioning rules.

### 14. Governance And Change Control
Keep this practical, not bureaucratic.

Recommended rules:
- Subsystem owners can change internals freely if public contracts remain stable.
- Changes to shared schemas, event types, persistence formats, or core invariants require RFC-style discussion.
- UI presentation can iterate quickly as long as replayability and contracts are preserved.
- Architecture should be re-reviewed after the expected first major redesign, then frozen again.

### 15. Delivery Phases
Anchor the document to a build sequence that supports learning without chaos.

Recommended phases:
1. Vertical slice: one guided prompt, one intent, one retrieval path, one rendered panel, one persisted session.
2. Session replay slice: serialize events and reconstruct the interface on reload.
3. Optional LLM slice: paraphrase or summarize deterministic content with guardrails.
4. Caching and sharing slice: add session URLs and cached variants.
5. UX expansion slice: richer prompts, contextual transitions, expanded panel system.

## Example Artifacts The Final Architecture Document Should Contain
The document should include these concrete artifacts, not just mention them:
- One system diagram in plain text or Mermaid.
- One end-to-end request sequence.
- One canonical content schema example.
- One intent router input/output example.
- One retrieval response example.
- One LLM-safe transformation example.
- One event log example.
- One persisted session example.
- One API contract example.
- One test matrix table.

## Recommended Test Matrix Format
For each test in the architecture doc, include:
- Test name.
- Subsystem owner.
- Input fixture.
- Expected output.
- Contract being protected.

This makes the architecture document actionable for implementation and CI planning.

## Suggested Writing Style
The final document should be:
- Prescriptive on interfaces and invariants.
- Flexible on internal implementation details.
- Concrete and example-driven.
- Short enough to stay usable, but specific enough to prevent accidental divergence.

Recommended tone:
- Internal engineering spec.
- Direct and constraint-oriented.
- Avoid vague product language when describing contracts.

## Execution Plan For Authoring The Document
1. Write the framing and invariants first so scope is locked before subsystem details.
2. Define the canonical content model and session/event model next because they are the main shared contracts.
3. Define router, retrieval, LLM, renderer, and persistence interfaces in that order.
4. Add example payloads immediately after each contract section so contributors can build against fixtures.
5. Add the testing section after contracts are defined, using the same example fixtures.
6. Finish with ownership, governance, and phased delivery guidance.
7. Tighten the document by removing any implementation detail that is not necessary for cross-team coordination.

## Key Risk To Address In The Final Document
The biggest architectural risk is accidentally building a chatbot-shaped system with weak contracts. The document should repeatedly reinforce that the system is a deterministic content interface with optional AI presentation, not an open-ended conversational agent.

## Success Criteria
The architecture document is successful if:
- Two different junior teams can implement against shared contracts without frequent re-alignment.
- The frontend can replay a session from saved state without needing saved HTML.
- The system still works coherently when the LLM layer is turned off.
- Canonical content remains authoritative across all render modes.
- Major integration points are covered by shared examples and tests before implementation fans out.
