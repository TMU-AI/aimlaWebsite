# MVP Architecture Document Plan

## Goal
Produce one MVP architecture document for a complete rewrite of the website.

The MVP should capture a deliberately simple first implementation shape:
- a small allowlisted set of valid content blocks or pages
- a thin resolver that maps user input to one valid block
- deterministic structured content behind each block
- strict fallback behavior for unsupported input
- a frontend that can be deployed simply on Vercel
- no requirement to preserve the current website's layout, navigation model, or implementation details

## Source Context
This plan should treat the current website as non-binding except for one operational constraint:
- deployment on Vercel should remain viable

Relevant context still worth acknowledging:
- `docs/architecture/planned/ai-native-website-architecture.md` describes the richer long-term direction.
- The MVP should be intentionally smaller and simpler than that target-state design.
- The user wants the original block-selection model as the first implementation, with room to evolve later.

## Key Product Decision
The first MVP should be framed as:
- a constrained content-block selector
- not a chatbot
- not a panel/event-stream system
- not a session-replay product
- not a service-heavy architecture

The document should make clear that this is a clean-slate rewrite, not a refactor of the existing site.

## Recommended Deliverable
Create one new planned architecture document, likely at:
- `docs/architecture/planned/mvp-block-resolver-architecture.md`

Recommended title:
- `MVP Block Resolver Architecture`

Recommended role relative to existing docs:
- This new MVP doc becomes the implementation source of truth for the first rewrite.
- `planned/ai-native-website-architecture.md` remains the longer-term evolution document.
- The MVP doc should reference the AI-native doc as a later expansion path, not as a requirement for the first slice.

## Document Intent
The MVP document should do three things clearly:
1. Freeze the minimal contracts junior developers need now.
2. Constrain the rewrite so it does not drift into chatbot behavior or architecture overreach.
3. Preserve a clean upgrade path toward the richer AI-native architecture later.

## Recommended Architectural Position
The MVP doc should commit to these points near the top:
- The system is a constrained content-block or page selector, not a general chatbot.
- There is a small allowlisted set of valid destinations.
- User input resolves to one valid destination or a fallback suggestion state.
- Canonical content is deterministic and structured.
- Blocks are rendered from structured data, not opaque generated markup.
- The MVP should remain operationally simple enough for straightforward Vercel deployment.
- The MVP does not require backend persistence, streaming, or LLM augmentation.
- Future AI-native behavior may be layered on later without changing canonical content ownership.

## Recommended Document Outline

### 1. Purpose And MVP Framing
Define:
- What the MVP is.
- What the MVP is not.
- Why the first rewrite is intentionally constrained.

Recommended non-goals:
- No open-ended chatbot responses.
- No LLM-generated canonical facts.
- No session replay or shareable sessions.
- No streaming renderer contract.
- No fine-grained retrieval pipeline in the MVP.
- No backend dependency unless Vercel-hosted serverless behavior is explicitly needed later.

### 2. Architectural Invariants
Keep this short and prescriptive.

Recommended invariants:
- The resolver may return only allowlisted block IDs.
- Unsupported input must produce deterministic fallback suggestions.
- Canonical content is structured and repo-managed.
- Rendered output is chosen from known blocks, not generated ad hoc.
- The MVP must be deployable on Vercel with a simple operational model.
- Any later AI layer may change presentation only, never canonical facts.

### 3. System Shape
Describe the MVP as a simple pipeline:
- User input.
- Input normalization.
- Block resolver.
- Structured content lookup.
- Render selected block or page.
- Fallback suggestion state when no valid block is selected.

Include one plain-text or Mermaid diagram.

Recommended flow:
```text
User input
  -> Block resolver
  -> Valid block ID or fallback suggestions
  -> Structured block content
  -> Render selected page or block
```

This section should avoid assuming:
- current section IDs
- current scroll behavior
- current single-page composition
- current component hierarchy

### 4. Valid Block Model
Define the allowlisted output space explicitly.

Recommended initial examples:
- `about`
- `events`
- `members`
- `join`
- `contact`
- `faq` only if the team intends to build it in MVP

The document should specify:
- stable block IDs
- human-readable labels
- what counts as a valid destination
- whether the MVP treats them as pages, views, or content blocks
- whether the frontend may implement them as routes or in-app state targets

Important guidance:
- Because this is a rewrite, the document should define the output model in product terms, not by inheriting the current site structure.
- If the team wants route-based navigation in the rewrite, the MVP doc may allow it.

### 5. Resolver Contract
This is the MVP replacement for the richer intent router.

The document should define:
- accepted inputs: guided prompt click, limited keyword text, search-like query, button selection
- normalization rules for user text
- alias mapping behavior
- resolver output shape
- minimal confidence model
- fallback behavior for unsupported input

Recommended resolver output example:
```json
{
  "match": "events",
  "confidence": "high",
  "reason": "keyword_match"
}
```

Recommended fallback example:
```json
{
  "match": null,
  "confidence": "low",
  "reason": "unsupported_request",
  "suggestions": ["about", "events", "join"]
}
```

Recommended rule:
- The resolver should never return arbitrary destinations, freeform answers, or inferred facts.

### 6. Structured Content-Block Model
The document should make clear that blocks are static outputs backed by structured data.

Define, at minimum, one content shape per major destination.
Recommended examples:
- `about`: title, summary, body blocks, media items
- `events`: title, intro, upcoming items, past items
- `members`: title, groups, member records
- `join`: title, CTA copy, links, forms
- `contact`: title, channels, external links

The document should specify:
- required vs optional fields
- stable IDs where reuse is expected
- validation rules for links, dates, and content visibility if applicable
- where content lives in the repo at a high level

The key message should be:
- the block/page is the MVP render target
- structured content inside that block is the maintainable source of truth

### 7. Rendering Contract
Keep this intentionally lightweight.

The document should specify:
- the UI receives a resolved block ID and renders the matching destination
- the frontend implementation may use routes, view state, or another simple mechanism consistent with the rewrite
- the renderer is not required to support conversational panel composition
- deterministic fallback views are allowed for unsupported input
- the final implementation should remain compatible with static or near-static deployment on Vercel

This section should avoid overcommitting to a single frontend composition pattern unless the team has already chosen one.

### 8. Unsupported Input Behavior
This section should be explicit because it is the main anti-chatbot safeguard.

The document should specify:
- unsupported input does not produce generated answers
- the system returns a constrained fallback state
- fallback shows a small set of valid destinations or prompts
- wording may be friendly, but the output remains deterministic

Recommended example behavior:
- Input: `Tell me about AI jobs in Toronto`
- Output: fallback suggestions such as `about`, `events`, `join`

### 9. Deployment And Runtime Assumptions
Because the current site architecture is intentionally non-binding, the MVP doc should explicitly define only the runtime assumptions that matter.

Recommended points:
- deployment must remain viable on Vercel
- the frontend should prefer static assets and simple runtime behavior where possible
- serverless functions are optional, not required, unless the rewrite later proves a need
- the MVP should avoid architecture that depends on long-lived backend sessions or complex infrastructure

### 10. MVP Test Matrix
The document should contain a compact, concrete test matrix.

Recommended categories:
- resolver match tests
- resolver fallback tests
- alias mapping tests
- content schema validation tests
- render-target tests
- deployment smoke tests if useful

Recommended test examples:
- given `events`, the resolver returns `events`
- given `members`, the resolver returns `members`
- given approved alias text, the resolver maps to the correct block
- given unsupported text, the resolver returns fallback suggestions and no generated answer
- given valid content for a block, the frontend renders the matching destination
- given a production build, deployment remains compatible with Vercel hosting assumptions

### 11. Ownership And Parallel Work
Keep team boundaries simple.

Recommended split:
- frontend: render resolved destinations, build navigation or selection UI, handle fallback state
- content/data: define structured block data files and normalize schemas
- resolver logic: implement normalization, alias mapping, and constrained matching
- architecture owner: keep the MVP compatible with future AI-native evolution without pulling that complexity into the first slice

### 12. Evolution Path
This section is important so the MVP document does not dead-end the system.

Document should explicitly state which seams are preserved for future growth:
- stable block IDs
- structured content under each destination
- a dedicated resolver module
- optional future subsection targeting such as `events:upcoming`
- optional future shift from block selection to structured retrieval
- optional future LLM presentation layer that never owns facts
- optional future service boundaries if the rewrite later needs them

Recommended framing:
- the MVP is a deterministic block selector now
- the later architecture may evolve into finer-grained retrieval and AI-mediated presentation
- that evolution should preserve content authority and constrained fallback behavior

## Example Artifacts The MVP Document Should Include
The final document should include these concrete artifacts:
- one high-level system diagram
- one valid-destination table
- one resolver input/output example
- one unsupported-input example
- one block content schema example
- one normalized events or members example
- one test matrix table
- one short section comparing MVP scope vs later AI-native scope

## Recommended Writing Style
The MVP architecture document should be:
- shorter than the AI-native target-state doc
- highly concrete
- prescriptive about current MVP boundaries
- intentionally narrow in scope
- easy for junior developers to map onto implementation tasks
- written as a rewrite spec, not as an adaptation of the current site

Recommended tone:
- internal engineering spec
- direct and constraint-oriented
- avoid carrying forward current-site assumptions unless they are truly intentional

## Risks To Address In The Final Document
The document should directly prevent these failure modes:
- overbuilding a chatbot instead of a block selector
- overfitting the rewrite to the current website structure
- introducing backend or streaming complexity too early
- treating blocks as opaque blobs instead of structured maintainable content
- failing to leave clean seams for the richer AI-native architecture later
- accidentally choosing an architecture that is awkward to deploy on Vercel

## Success Criteria
The MVP architecture document is successful if:
- junior developers can tell exactly what the first rewrite should do
- the valid output space is clearly bounded
- the resolver contract is simple enough to implement without ambiguity
- the content boundary is structured enough to support future growth
- the document leaves a clear path toward the richer AI-native architecture without importing that complexity into MVP
- deployment assumptions stay simple and Vercel-compatible

## Implementation Notes For The Later Authoring Pass
When writing the actual MVP document:
1. Open by stating that this is a clean-slate rewrite and that the current website structure is not a constraint.
2. Contrast MVP scope explicitly with `planned/ai-native-website-architecture.md` so the team does not blend the two.
3. Prefer `block resolver`, `page resolver`, or `destination resolver` over `intent router` unless the term is intentionally defined.
4. Define valid destinations in product terms, not by mirroring the current site.
5. Keep the rendering section implementation-agnostic enough to allow either route-based or view-state-based navigation.
6. Keep the deployment/runtime section explicit so Vercel compatibility remains a real constraint.
7. End with a short evolution section rather than mixing MVP and long-term architecture throughout the whole document.
