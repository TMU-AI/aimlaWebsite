# Architecture Documents Plan

## Goal
Generate a small set of architecture documents for the TMU AIMLA website that are grounded in the current codebase and then refined against the user's intended future direction.

## Current Repo Snapshot
- Stack: React 17 + Create React App + styled-components + framer-motion + locomotive-scroll.
- App shape: single-page marketing/community site composed in `src/App.js` from section components.
- Main sections: `Home`, `About`, `Events`, `Team`, `Join`.
- Navigation model: in-page anchor navigation plus a scroll indicator driven by section IDs.
- Content model today: content is mostly hardcoded directly inside React components.
- Styling model: global theme tokens in `src/styles/Themes.js` and global CSS reset/fonts in `src/styles/GlobalStyles.js`.
- Deployment note from `README.md`: static build, also deployed on Vercel.

## Selected Documentation Set
1. System Overview
- Lean maintainer-focused description of site purpose, boundaries, users, and runtime model.

2. Frontend Architecture
- Application composition, section/component structure, styling system, animation/scroll behavior, and asset organization.

3. Future-State Architecture
- Target-state direction for CMS/content editing, event publishing workflow, analytics/SEO, and preserving a static-accessible delivery model.

## Confirmed User Decisions
- Primary readers: maintainers and future student handoff.
- Scope: both current-state and future-state.
- Tone: lean internal documentation.
- Priority first-draft docs: system overview and frontend architecture, with future-state guidance included.
- Expected evolution themes: CMS/content editing, event publishing pipeline, analytics/SEO, and a static webpage model with accessibility as a key constraint.
- Future content-management direction: structured repo data files rather than a headless CMS for the first target-state recommendation.
- Future event update ownership: both maintainers and non-technical editors should be supported.
- Analytics/SEO recommendations: light guidance, not a deeply prescriptive tooling decision.
- Diagrams: omit from the first draft.

## Documentation Approach
- Start with an accurate current-state architecture extracted from the repo.
- Layer the user's vision on top of that as a target-state or roadmap section.
- Keep docs practical and maintainable rather than enterprise-heavy.
- End with a refinement pass to tighten terminology, level of detail, and recommendations.

## Draft Outline
1. System Overview
- Purpose of the site.
- Primary user groups and maintainer audience.
- Runtime boundaries: browser app, static hosting, external form/social dependencies.
- High-level architectural constraints and assumptions.

2. Frontend Architecture
- Entry points and composition flow (`index.js` -> `App.js` -> section components).
- Section architecture and in-page navigation model.
- Shared UI elements such as nav, scroll indicator, logo, and cover video.
- Styling/theming approach with `styled-components` and theme tokens.
- Content placement today and its maintenance implications.
- Asset organization and external dependencies.

3. Future-State Architecture
- Static-first target state that preserves accessibility and operational simplicity.
- Move mutable content into structured repo data files instead of hardcoding inside components.
- Define an event publishing workflow that can be maintained by both technical and non-technical contributors.
- Add light analytics/SEO guidance without tightly coupling the docs to a specific vendor.
- Describe recommended separation between content, presentation, and operational ownership.
- Clarify whether a backend is actually needed, and if so, define subsystem boundaries and interface contracts before parallel implementation begins.

4. Refinement Pass
- Tighten wording and terminology.
- Validate that recommendations match club capacity and workflow reality.
- Trim unnecessary detail and fill any handoff gaps.

## Execution Plan
1. Draft the selected architecture docs from the current repo structure.
2. Frame the current-state issues around maintainability, hardcoded content, and static deployment assumptions.
3. Add a future-state recommendation centered on structured repo data files, shared event editing ownership, and static-first accessibility.
4. In that future-state section, explicitly decide whether the system remains static-only or introduces backend services.
5. If any backend/services are introduced, define subsystem interfaces immediately after the future-state architecture is chosen and before work is split across juniors.
6. Keep analytics/SEO guidance light and implementation-agnostic.
7. Run a final refinement pass focused on clarity, maintainability, and realism for future student handoff.

## Backend and Interface Timing
- Clarify backend design during the first draft of the future-state architecture, not at the very end.
- The correct sequence is: product vision and constraints -> decide static-only versus service-backed features -> define subsystem boundaries -> define interface contracts -> then split work across contributors.
- For this repo's current state, there is no meaningful backend architecture to document beyond static hosting and external dependencies.
- For the future-state, backend and subsystem interfaces should be treated as the first thing to freeze once you decide to add capabilities like managed content publishing, authenticated admin workflows, or service-owned data.
- If the future-state stays static-first with repo data files, the main interfaces to define are likely content schemas, build-time data loading boundaries, and frontend component contracts rather than network APIs.

## Initial Observations To Validate
- This repo currently represents a presentation-oriented site, not a multi-page application or service-backed product.
- The biggest architectural constraint today is content being embedded directly in UI components.
- The most likely documentation value is maintainability/handoff clarity rather than complex distributed-system design.
- The most important future-state choice is likely whether content editing stays Git-driven or moves to a non-code publishing workflow.
